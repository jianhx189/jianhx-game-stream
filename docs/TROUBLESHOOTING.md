# MiniStream — 自用极简低延迟游戏串流工具

两个 exe 走自定义 TCP+UDP 协议，直连 `IP:端口` + 验证码即可用。
被控端采集屏幕 + NVENC 硬编 + UDP 发送；远控端 UDP 收包重组 + D3D11VA 硬解 + 无垂直同步渲染 + 键鼠回传。

**本机实测（RTX 4060 Ti，1080p60 回环）：60.0 fps / 20 Mbps / 丢帧 0.0% / 端到端 14 ms / 编码 2.4 ms / 解码 0.8 ms，硬编硬解全程 GPU。**

## 特性（本轮打磨后）

这些不是"我们自己想的"，而是逐条对照 Moonlight / RustDesk / UU远程·GameViewer / Parsec
四份成熟产品的源码与二进制逆向抄来的工程设定（细节见 `docs/OPTIMIZATIONS.md`）：

- **UDP 视频 + XOR-FEC + NACK 重传**：每 G 片 1 个校验包（5%~25% 自适应开销）+ 缺片 12ms 内
  请求重传（每帧最多 2 次、40ms 截止、重传流量限速 15%），丢一片不再废整帧
- **拥塞控制对齐 RustDesk/Parsec**：默认码率 1080p60 ≈ 8 Mbps（不再 20 Mbps 打爆中继）；
  以**排队延迟**为主信号分档降码率（>500ms×0.5 / >300×0.7 / >150×0.9），
  升档 ×1.10 且每秒 ≤+450 kbps；UDP 发送端有 **cwnd 在途字节上限**（Parsec/SCTP 同款思路）
- **反花屏铁律**：缺帧立即停解等 IDR，**绝不把不完整帧喂解码器**；
  按需 IDR（无周期 IDR）+ 600ms 最小间隔 + IDR 关键帧双份发送
- **H.265 热切换**：画质面板一键 H.264 ↔ H.265，中继带宽紧张时同画质省 30~40% 码率
- **输入不排队**：键鼠默认走 UDP + 3 份冗余（报告实测这是"鼠标不卡"的前提）；
  被控端 `SetCursorPos` 失败自动改走 `SendInput`（修掉独占全屏下"断触"）
- **MMCSS 线程调度** + 交换链三重缓冲 + 等待对象（Present 不阻塞主循环）
- **TCP 兜底不再越用越卡**：码率压 12 Mbps + 发送超一帧间隔就跳帧追赶
- **双线 FRP 容灾**：`backup_host/backup_port` 失败自动换线重试；掉线自动重连
- **客户端常驻托盘**：关窗口=后台运行，双击托盘恢复，右键退出

---

## 它解决什么

Moonlight + Sunshine 配置体系太重、安全策略冗余。这里只保留串流和输入回传必需的东西：

- 不做 P2P 打洞 / STUN / TURN / 中心信令 —— 你已有 FRP 和公网 IP，直连即可
- 不做多用户 / 账户系统 / 云端
- 只支持 Windows
- 不做文件传输 / 剪贴板同步
- 不做复杂加密（密码走挑战-应答 HMAC，视频流不加密，见 `docs/PROTOCOL.md` 的取舍说明）

## 结构

```
src/common/   协议、加密、网络、配置、统计、画质档位定义（零第三方依赖，SHA-256/HMAC 自带）
src/host/     被控端：DXGI 采集 -> GPU NV12 -> NVENC/AMF/QSV -> UDP 分片
              + SendInput 注入 + 托盘/配置窗口
src/client/   远控端：UDP 重组 -> D3D11VA 硬解 -> D3D11 渲染（关 vsync）
              + Raw Input 捕获 + D2D 悬浮状态条 + 连接面板 + 会话工具栏
tests/        selftest（77 项协议/画质/加密自检）、videoprobe（不联网的采集+编码探针）
docs/         BUILD（编译）、PROTOCOL（协议规范）、USAGE（使用与排障）
```

## 快速开始

1. **被控端**（游戏主机）：`ministream-host.exe`。首启动会在 exe 旁生成 `host.ini`。
   托盘图标右键 → 打开配置，改**端口**（默认 20000，必须 >10000）和**验证码**。
   也可以直接 `--headless` 无界面跑（见 `docs/USAGE.md`）。
2. **FRP**：同一个端口要配**两条**规则——一条 TCP、一条 UDP（TCP 走控制/握手，UDP 走视频与输入）。
3. **远控端**（本地电脑）：`ministream-client.exe`，打开 RustDesk 风格的连接面板：
   一个输入框直接粘 `IP`、`IP:端口` 或 `域名`，填验证码即可连。
   面板上选好**画质档位**（均衡 / 画质优先 / 流畅优先）或手动指定分辨率/帧率/码率。
   连不上会把失败原因**红字显示在面板里**（不弹窗），改完参数直接重连。

### 远程中的顶部工具栏（RustDesk 式）

游戏中按 `Ctrl+Alt+Shift+Q` 释放键鼠，工具栏立刻出现在窗口顶部：

```
1920 x 1080 · 60 fps · 20 Mbps · 延迟 16 ms · 丢帧 0.0%   [画质▾] [全屏] [☑悬浮条]      断开连接
```

点 **画质▾** 展开面板，可调：预设档位、分辨率（原生/1080p/1440p/4K/…）、
帧率（30/60/120/144）、码率（自适应/8/15/20/30/50/80 Mbps 或自定义）、关键帧间隔。

- **只改码率/关键帧间隔 → 热调**，画面完全不断
- **改分辨率/帧率 → 自动重协商**，中断约 0.27 秒后无缝恢复（实测零丢帧）
- 工具栏**不抢焦点**（`WS_EX_NOACTIVATE`），点完按钮焦点自动回到渲染窗口，
  游戏中不会被打断；离开 3 秒自动收回

构建方法见 `docs/BUILD.md`，协议细节见 `docs/PROTOCOL.md`，完整使用与排障见 `docs/USAGE.md`。

## 延迟预算（本机实测）

| 环节 | 耗时 |
|------|------|
| BGRA→NV12（GPU VideoProcessor，含缩放） | 1.5 ms |
| NVENC 编码（p1 + zerolatency + CBR） | 2.4 ms |
| 网络 | — |
| D3D11VA 解码 | 0.8 ms |
| 呈现（Present 0 + ALLOW_TEARING） | <1 ms |
| **端到端（采集→呈现）** | **14 ms** |

两个决定成败的开关：**渲染必须关垂直同步**（否则每帧白等一个刷新周期），
**任何一级缓冲都不许积压**（重排队列深度 2、满了丢最旧；发送端内核缓冲满就整帧放弃）。

## 稳定性修复：被控端"连接后黑屏、然后闪退"

**现象**：连上之后画面黑一下，被控端进程消失。Windows 事件日志记
`ministream-host.exe` 异常码 `0xC0000409`。

**定位过程**（可复现，不是猜的）：

1. 从 `%LOCALAPPDATA%\CrashDumps` 取到真实转储，`tools\minidump_info.py` 解出
   fast-fail 子码 = 7（`abort`），栈上是 VCRUNTIME 的异常帧、异常来自 accept 线程。
2. 用只加 `/MAP` 的构建（与发布版仅差 PE 头 4 字节）把栈翻译成函数名：
   `ms::log_write` + `"accept: %s"` + `"WARN "` —— 正好是日志里最后那行
   "accept 失败，错误码 10038"。
3. 于是根因明确：`HostService::Impl::accept_loop()` 退出时的收尾代码把
   `publish()` 写在了 `statMtx` 的作用域**内部**，而 `publish()` 自己会再锁一次
   同一把非递归 `std::mutex`。UCRT 判定为"必然死锁"，`lock()` 抛
   `std::system_error`；accept 线程里没人接，`__std_terminate` → `abort` → 进程消失。
   触发条件就是"accept 线程退出外层循环"，也就是**停止服务 / 退出程序**的时候。

**一并修掉的同类隐患**（都是"能崩一次就能崩第二次"的类型）：

- `stop()` 现在用互斥量串行化：以前两个 `stop()`（托盘"停止服务"+"退出"+析构）
  会**同时 join 同一个 `std::thread`**，MSVC 下同样抛 `std::system_error`。
  join 统一走 `join_thread()`（先把句柄搬到锁外，谁搬走谁 join）；
  accept 线程自己负责回收会话线程，`stop()` 只 join 它一个。
- 所有线程函数（accept / stream / input / 客户端 control）都包了 `try/catch`：
  线程里逃逸的异常在 MSVC 下**不会**走 `std::set_terminate`，而是直接 abort；
  现在会被记进日志并抑制。
- 新增 `src/common/crash.{h,cpp}`：未捕获异常、访问越界、CRT 非法参数都会写
  `crash.log`（含类型、`what()`、调用栈）和 `.dmp` 转储，不再只弹系统错误框。
- 客户端工具栏的状态字曾被**控制线程**直接写窗口控件（`SetWindowTextW`），
  与 UI 线程并发读写 `std::wstring` 有堆破坏风险；现在统一 `PostMessage`
  回 UI 线程刷新。
- 被控端加**单实例守卫**：第二个实例直接退出，避免抢端口 / 两份日志互相覆盖。
- 托盘"保存"配置后**立即按新配置重新监听**（端口/密码改完就生效）；
  内容没变则不重启，不打断正在进行的会话。

**验证**（脚本都在 `scripts\`）：

| 证据 | 结果 |
|------|------|
| `abtest.ps1`：同一场景（托盘被控端 + 真实客户端串流 + 停止服务）跑新旧两个二进制 | 旧版 `-1073740791`（0xC0000409）崩溃；修复版 `0` 正常退出 |
| `ministream-selftest.exe` | **89/89**，含并发 stop / 会话中 stop / 断线重连 / 8 次启停 / 真实握手 |
| `regress.ps1` | 单实例守卫生效（第二实例退出码 6）；空保存不打断会话；退出码 0，无转储 |
| 端到端（动图源、1080p60、20 Mbps） | 60 fps、0% 丢帧、端到端 16.1 ms、解码 0.73 ms、编码 2.4 ms |

## 稳定性修复二：会话结束后被控端"再也连不上"

**现象**：第一次能连上（画面正常），远控端一断开，之后再连就黑屏或直接连不上；
被控端进程还在托盘里，但 TCP 端口已经不监听了（`netstat` 查不到 14738）。

**根因**：`input_loop_body()` 的循环条件只有 `running && !stopReq`，
**漏了 `sessionActive`**。所以会话结束后输入线程永远不退出，
负责收尾的 `join_session_threads()` 里 `join(thInput)` 永久阻塞 —— accept 线程卡死，
再也回不到 `listen`。只有点"停止服务"（`stopReq`）才退，这正好解释了为什么
自测的"启动/停止"用例全过、真机连一次就废。

**修复**：循环条件加上 `sessionActive`，并新增自检用例
「远控端断开后被控端自动回到监听 + 断线后可以再次建立会话」——
去掉这行修复，该用例必失败。

## 稳定性修复三：日志不再可能冻死整个进程

`log_write()` 原来无条件调用 `OutputDebugStringA()` 和 `fputs(stderr)`。
这两者在部分机器上会**阻塞**（装了输入法/远程控制/虚拟显示器/游戏加速器这类
会挂调试输出监听器或接管控制台的软件时很常见），而日志写在全局锁里做的，
一旦阻塞就是全进程所有线程一起卡住。现在：

- 只在 `IsDebuggerPresent()` 为真时才发调试串；
- 控制台输出默认关闭，只有 `--auto` 脚本模式才打开；
- 日志文件仍然每行 `fflush`，崩溃时照样留得下。

**心跳阈值同步放宽**（被控端 20 s / 远控端 25 s）：实测有的机器会话刚建立时
会整进程停顿 5~10 秒，期间一个 Ping 都发不出来，原来的 3 s / 8 s 会把它误判成掉线，
表现就是"连上黑屏几秒然后断开"。

## 稳定性修复四：真机"卡在等首帧 / 黑屏 / 几秒后断开"的两个真正根因

这两个都是**只在特定机器上才暴露**的问题，本机（开机几小时）怎么测都正常，
在客户端那台**开机 20 天的机器**上一测就现形。

### 根因 1：`now_us()` 溢出 → 一个心跳都发不出去

`now_us()` 原来是 `(QueryPerformanceCounter() * 1000000) / freq`。
`freq = 10 MHz` 时，**开机超过约 10.7 天**这个乘法就超过 `int64` 上限、溢出成负数
（实测那台机器：`c*1e6 = -638746045920551616`，`now_us() = -63874604592`）。

而代码里 `lastPingUs_ = 0`、`lastStatsUs = 0` 用 0 当"从未"的哨兵：

- `now - 0 >= 500ms` 永远不成立 → **一个 Ping 都发不出去** → 被控端超时踢人；
- 统计日志同理永远不打印 → 日志看起来就像"卡在等首帧"；
- 客户端自己的判死计时基准是负数，也失效了。

修复：`us_from_ticks()` 改成"先除后乘、余数单独换算"，全程不溢出；
所有时间哨兵改用 `now_us()` 初始化，不再依赖时钟为正。自检里加了
「开机 20 天换算仍为正且 1 秒增量准确」的回归用例。

### 根因 2：多网卡回包源地址不对 → 视频全被 FRP 丢掉

被控端机器上 `192.168.1.10` 在 **vEthernet（虚拟网卡）**、`192.168.1.11` 在
**以太网（物理网卡）**。frpc 配置 `localIP = 192.168.1.10`，把 UDP 送到 `.204`；
我们的 UDP 套接字绑的是 `0.0.0.0`，**回包源地址由路由表决定 → 走了物理网卡变成 `.202`**。
frpc 那边是 `connect()` 过的 UDP 套接字，只认它发过去的 `.204`，源地址不对的回包
被系统直接丢弃。于是：**上行（客户端→被控端）通，下行（视频）全丢**，
客户端一个视频包都收不到 = 永久黑屏。

修复：会话建立后把 UDP 套接字**绑定到客户端实际连进来的那块本机 IP**
（`TCP getsockname` 拿到），会话结束再恢复 `0.0.0.0`。另外这个重绑路径必须
显式设 `非阻塞`——输入线程是按非阻塞写的，套接字若保持阻塞，收包线程会在
`recvfrom` 里睡死，会话结束时 join 卡 30 多秒（自检里已加回归覆盖）。

### 顺带修掉：端到端延迟显示 0.0 ms

`ClockSync` 的偏移符号写反了（`offset = 远端 - 本地`，换算却写成 `+offset`）。
内网/环回 `offset≈0` 所以一直没发现；一跨公网延迟就变成负数、被统计模块丢弃，
显示成 `0.0 ms`。改成 `本地 = 远端 - offset`、`远端 = 本地 + offset`，并加
"两种换算互为逆运算"的自检用例。

## 稳定性修复五：真机"只看到一小块 / 变色 / 一闪一闪"（画面正确性 + 稳定性）

### 根因：渲染 UV 推导错了（画面被放大成左下四分之一）

全屏大三角形的顶点参数 `p` 范围是 `0..2`，屏幕可见区域对应 `p∈[0,1]`，
所以 **UV 必须直接等于 `p`**。原代码写成了 `p * 0.5`，等于只采样纹理的
**左下四分之一并放大 2 倍** —— 真机表现就是"连上了，但只看到远端桌面的
一角，还以为分辨率没适配"。用一张带网格和四角标记的参考图放到被控端全屏，
两端同时截图对比即可复现（修复前后各抓一张，差异一目了然）。

**注意**：本地测试一直"看得见画面"所以从来没发现——只验证了 fps/丢帧，
没验证画面内容。这类问题必须用参考图 + 截图对比。

### 视频传输改成「UDP 优先 + 自动 TCP 回退」（RustDesk 同思路）

FRP 的 UDP 反向链路在部分网络/配置下不可靠（实测：上行 PING 全通、下行回包
全丢）。现在的策略：

1. 默认走 UDP（延迟最低）；
2. 会话建立 2.5 秒仍没有视频包 → 自动请求被控端改走 **TCP 传整帧**
   （新消息 `VideoOverTcp` / `VideoFrame`，控制通道已加发送锁）；
3. UDP 丢帧超过 8 帧（花屏/变色/闪）→ 同样自动切 TCP；
4. TCP 模式下画面零丢包，代价是延迟略高（实测 11~30ms，打游戏完全可用）。

### 抗丢包：NVENC intra-refresh

编码器打开 `intra-refresh`：帧内刷新片逐帧扫过全画面，丢包造成的花屏会在
1 秒刷新周期内自愈，不用等下一个 IDR。配合原生 1~2 秒 GOP，UDP 偶尔丢 0.5%
也不会再出现"长时间花屏/变色/一闪一闪"。

### 自适应码率

每 2 秒看一次丢帧率：`>3%` 就按 20% 降码率、`<0.5%` 就慢慢升回协商上限，
避免公网抖动时固定码率持续超出链路能力。

### 显示模式可选（工具栏"缩放"按钮循环）

- **智能缩放**（默认）：等比缩放 + 黑边，任何窗口都能看全；
- **拉伸填充**：铺满窗口/屏幕，可能变形；
- **原始大小 1:1**：像素精确，画面比窗口大时居中裁切。

### 顺带修掉的

- **被控端 UDP 来源漂移**：原策略"连续 200 个包才认新地址"（2 秒一个保活
  包 = 400 秒），FRP 端口一变就整场黑屏。现在连续 4 个包就跟随并补 IDR。
- **多网卡回包源地址**：会话建立时把 UDP 绑到客户端实际连入的本机 IP
  （本机有 `192.168.1.10` 虚拟网卡 + `192.168.1.11` 物理网卡两个 IP，
  绑 `0.0.0.0` 时回包源 IP 由路由决定，FRP 的 connected UDP 会丢弃）。
- **DPI 感知**：进程声明 Per-Monitor V2，避免 125%/150% 缩放机器上坐标错位。

**真机实测**（经 `192.0.2.10:14738` FRP）：1080p60、20 Mbps、UDP 丢帧
0.3~0.8%（intra-refresh 自愈）、端到端 29.7 ms、RTT 24 ms；强制 TCP 模式
0% 丢包、端到端 11.4 ms；两张间隔截图哈希一致（无变色/闪烁）。

## 稳定性修复六：鼠标不见了 / UDP 抖一下就永久吃 TCP

### 问题 1：连上去看不到鼠标（游戏里藏光标、菜单里要显示）

**根因**：Desktop Duplication 给出的桌面纹理里**没有光标**——光标是系统在合成层
单独画的。旧版本只发视频，远控端又为了游戏把本机光标 `ShowCursor(FALSE)`
藏起来了，于是"两个都没有"，鼠标就彻底消失了。

**修复**（学 RustDesk 的 Windows 采集器）：

1. 被控端每帧调 `GetCursorInfo` 取「系统光标此刻是否可见 + 在哪」，
   调 `IDXGIOutputDuplication::GetFramePointerShape` 取光标图片
   （`MONOCHROME`/`COLOR`/`MASKED_COLOR` 三种格式统一转成**预乘 alpha 的 BGRA**）；
2. 位置/可见性走 **UDP**（几十字节，60Hz 也就几 kbps，跟手）；
   形状走 TCP（几 KB，只在形状变化时发，一场会话通常就几次）；
3. 远控端用 D2D 把光标画在视频之上，位置按当前缩放模式（智能/拉伸/1:1）换算；
   同时把本机系统光标藏起来，避免"两个鼠标"。

**为什么这样能自动区分"游戏菜单"和"游戏内场"**：本地打游戏时，游戏进内场会自己
`ShowCursor(FALSE)` 把系统光标藏起来、回菜单再显示。被控端的
`CURSORINFO.flags & CURSOR_SHOWING` 如实反映这个状态，远控端照抄即可：
**菜单里有鼠标、进游戏自动消失**，和本机玩的手感完全一致，不需要去猜"哪个是游戏"。

实测（真机 FRP，远端截图逐像素比对）：光标在指定位置画出、换形状（箭头/手型/文本
光标都正确）、被控端藏起光标时远端同步消失、恢复后又出现。

### 问题 2：UDP 抖一下 → 永久切 TCP，打游戏一直吃高延迟

旧逻辑是**单向**的：一旦切到 TCP 就再也不回来。现在改成双向自愈：

1. 只有在**真的断流**（1.2 秒收不到 UDP 视频包）或**大面积丢包**
   （1.2 秒窗口 >25%）时才切 TCP；偶发丢 1% 交给 intra-refresh 自己恢复；
2. TCP 模式下每隔 3 秒请求一次 **UDP 探测**：被控端在 0.9 秒窗口内**同时**用
   UDP 发视频，远控端拿同一窗口的 TCP 帧数当分母算到达率；
3. 连续两次探测 ≥70% 就自动**切回 UDP**（低延迟）；不够就指数退避
   （3→6→12→20 秒）继续探测，网络一好立刻恢复。

实测（真机 FRP）：开局强制切 TCP → 6 秒内两次探测（95%、98%）→ 自动切回 UDP；
再人为切断 UDP 视频 → 1.5 秒内切 TCP（探测 0% 保持）→ 恢复后探测 98%、96% →
自动切回 UDP。

> 排障用环境变量：`MINISTREAM_FORCE_TCP_VIDEO=1` 钉死 TCP；
> `MINISTREAM_TEST_TCP_START=1` 开局先切 TCP（验证自愈能否切回）。

## 稳定性修复七：鼠标"乱飘"/不像自己的鼠标（绝对映射）

**现象**：菜单/桌面里移动鼠标，远端光标乱飘，和本机鼠标位置对不上。

**根因**：之前所有鼠标移动都按**相对位移**注入（游戏内场需要），被控端用
`SendInput(MOUSEEVENTF_MOVE)` 注入后，Windows 的**鼠标加速（提高指针精确度）**
会把小位移放大/压缩，而且远控端按帧攒批发送，和本机鼠标的物理轨迹并不一致，
所以远端光标轨迹"像另一个鼠标"。

**修复**：按被控端上报的「系统光标是否可见」自动切两种模式：

| 场景 | 模式 | 行为 |
|------|------|------|
| 桌面 / 游戏菜单（系统光标可见） | **绝对映射** | 远控端把本机光标位置按缩放模式换算成远端像素坐标发过去，被控端 `SetCursorPos` 直接摆放 → **远端光标和你本机鼠标 1:1 重合**，完全不吃鼠标加速 |
| 游戏内场（游戏把系统光标藏起来） | **相对模式** | 藏起本机光标、发原始位移，游戏自己读 Raw Input（FPS 瞄准要的就是这个） |

不画"额外的远端光标"了：绝对模式下你的本机光标就是那个光标，所以不会出现
"两个鼠标/拖影"。切换点是 `client.log` 里的 `鼠标模式 -> 绝对映射` /
`鼠标模式 -> 相对模式`；`client.ini` 的 `input.mouse_mode = auto|absolute|relative`
可以强制（默认 auto）。

**真机实测**（客户机 VM 上把光标移到指定位置，读被控端真实光标位置）：

```
客户机鼠标(400,300)  -> 被控端光标(400,300)  误差 0 px
客户机鼠标(1500,800) -> 被控端光标(1500,800) 误差 0 px
客户机鼠标(960,540)  -> 被控端光标(960,540)  误差 0 px
模拟游戏内场（藏光标）: 鼠标模式 -> 相对模式
回到菜单（恢复光标）  : 鼠标模式 -> 绝对映射
```

## 修复九：TCP/UDP 一直切换、鼠标卡顿、画面局部花屏（照抄 Moonlight / RustDesk 的关键设定）

用户实测："tcp/udp 一直切换，鼠标卡顿，画面局部花屏屡屡出现"。逐条读
Moonlight（GameStream 客户端）与 RustDesk 的源码后，定位到三个真根因，并把它们
**公开的工程设定**直接搬过来（完整对照表见 `docs/OPTIMIZATIONS.md`，
交付包里叫 `OPTIMIZATIONS-优化设定.md`）。

### 1) 局部花屏：缺帧后还在解 P 帧 + intra-refresh 的"糊块"
- 照 Moonlight `VideoDepacketizer` 的做法加 **WAIT_IDR 状态机**：帧号不连续 / 丢帧 /
  解码报错 → 后续 P 帧一律丢弃、不喂解码器，只等关键帧；
- **请求 IDR 不在丢包瞬间**（那时求 IDR 会造成"IDR 尖峰→更多丢包"的拥塞崩溃），
  而是等丢包后第一个完整帧到了再发，100ms 节流 + 120 帧兜底；
- 编码器**关掉 intra-refresh**：它会把一个 IDR 摊成逐帧刷新的条带，丢包后画面上
  会留下"一条持续约 1 秒的糊块"——正是用户看到的局部花屏；
- 保留 2 秒 GOP + 按需 IDR，`repeat-headers=1`，`refs=1`、`slices=1`、无 B 帧。

### 2) 帧率腰斩：丢一个分片就废一整帧（新增 XOR-FEC）
- 1080p60 一帧 30~40 个 1200B 分片，链路丢 2% 包时整帧到达率只有 ~49%；
- 新增 `src/common/fec.h`（XOR 组码）：每 G 片配 1 个校验包，丢 1 片可无损恢复；
  组大小按客户端反馈的丢帧率自适应（4/5/8/12/20 → 25%~5% 开销，3 次同向才生效 + 死区）；
- **关键帧整体重发两遍**：IDR 是唯一恢复手段却比 P 帧大一个数量级，最容易丢。

### 3) 一直切换 / 鼠标卡顿：滞回状态机 + 输入不再被视频堵
- 切换判据改成"真的不能用"：断流 2 秒 / 整帧丢失 >30% 持续 3.5 秒 / **连续 2.5 秒
  等不到 IDR** 才切 TCP；切到 TCP 后 8 秒稳定期、每 5 秒探测一次（1.2 秒窗口），
  **连续两次到达率 ≥95%** 才切回；切回后有观察期（20s 起、每次抖动翻倍，最长 5 分钟）。
  实测 15% 丢包下只切一次并稳定保持，不再来回抖；
- 键鼠不再固定走 TCP：视频走 UDP 时键鼠走 TCP（可靠）；**视频切 TCP 时键鼠改走 UDP**
  + 状态事件 3 份冗余/移动 2 份，被控端按包序号整包去重；
- 鼠标移动合并到 ~500Hz（原来 1000Hz 事件几乎每个都单独成包），按键/滚轮不合并；
- 相对位移钳制 ±10000（RustDesk 同款），防止异常巨值把视角甩飞。

### 4) 呈现与解码：Moonlight 的低延迟组合
- 交换链 BufferCount 2→3 + `FRAME_LATENCY_WAITABLE_OBJECT` + `SetMaximumFrameLatency(2)`，
  渲染前等句柄：`Present(0)` 不再因为队列满而阻塞主循环（阻塞 = 输入/解码跟着顿）；
- 解码器补 `OUTPUT_CORRUPT` + `err_recognition=AV_EF_EXPLODE`，硬解单线程提交；
- 接收队列 2→3 帧（原来偶尔顶掉整帧就触发等 IDR）；
- 自适应码率增加 **排队延迟**信号（RustDesk QoS 思路）：端到端延迟相对近期最好值
  >150ms 直接降档，不等丢包发生；码率预算取协商值的 85%，剩下留给 FEC。

### 5) 顺手修掉的统计 bug（这条影响最大）
迟到的 FEC 校验包（数据片先齐、校验片后到）以前会为已完成的帧新建一个空的重组状态，
120ms 后超时被记成"丢了一整帧"。结果：**0% 真实丢包也会报 ~48% 分片丢失**，
自适应码率和 FEC 组大小全被带偏（越"优化"越卡）。现在迟到包直接丢弃，并新增
包级/帧级分离的统计（日志里 `丢帧 % / 分片丢 %` 两列）。

### 6) 第二批：照抄 UU远程 / GameViewer 的实测设定

参考 `D:\1\GM\GameViewer\串流流畅性工程设定分析报告.md`（对 GameViewer 4.31.1 的逆向分析，
18 份会话统计 + 5.8 万行逐秒时序）。抄进来的：

- **输入默认走 UDP（不是 TCP）**：TCP 最小 RTO 200ms，一次丢包就让鼠标粘住；
  实测那边输入延迟 18~22ms 且无长尾。我们改成 UDP + 每包 3 份冗余（状态事件隔 2ms 发），
  只有视频被迫切 TCP 时才回落到 TCP 输入。**这是"鼠标卡顿"的最大单项修复。**
- **无限 GOP + 按需 IDR + 600ms 最小间隔**：那边 24 万帧只有 7 个 I 帧。
  周期 IDR 的大帧会造成码率锯齿 → 队列堆积 → 规律性卡顿。默认 `keyframe_interval_sec=0`，
  工具栏关键帧选项第一项变成「按需（推荐）」。
- **VBV = 目标码率 × 5 ÷ fps**（60fps ≈ 83ms）：原来 buffer 取了 1 秒，等于攒了 1 秒的
  突发额度，复杂场景会瞬间打满队列。这条在那边 1615 次重配置里零误差。
- **NACK 重传（新增）**：缺片 12ms 后请求、10ms 节流、每帧 2 次；被控端保留 1 秒发送历史
  补发、重传流量限速 ≤15%；重传包打 `RETRANSMIT` 标记。FEC 打底 + NACK 主力，
  叠加后 5% 丢包下**帧丢失从 ~7% 降到 ~0%**。
- **按帧号顺序交付（25ms 重排缓冲）**：NACK 救回的帧可能比后续帧晚完成，
  直接入队会"乱序喂解码器"→花屏；现在新帧会等前序帧补齐（超时才跳号等 IDR）。
- **AIMD 码率按「每秒」**：无丢包 ×1.08/秒、丢包 4~13% ×0.94/秒、≥15% ×0.84/秒、
  排队延迟涨 ×0.90/秒、降额后 2 秒内不升；起步只给上限的 55%，不再一上来顶满。
- **延迟分位数 + jank 分级**：日志每 2 秒输出 `[延迟] p50/p90/p99 | jank 小/中/大`，
  验收口径同那边（小 33~100ms、中 100~1000ms、大 >1000ms；p99 <150ms、jank% <0.5%）。

**没照抄**（附理由，详见 `docs/OPTIMIZATIONS.md`）：KCP+RS-FEC（我们已把输入挪出可靠流，
不需要引入 KCP）、slice ≤1200B（与"整帧重组、不完整帧不送解码器"互斥）、
WebRTC 式 pacing 独立发送线程（改动大，先用 FEC+NACK 兜）、BGRA→NV12 shader 零拷贝
（已有 GPU 转换，编码实测 ~1ms 不是瓶颈）、NVAPI P-State/提权（收益边角、风险更高）。

> 自检：142/142（新增 FEC 编码/恢复单测）。
