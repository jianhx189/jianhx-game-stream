# MiniStream 与 RustDesk、Windows RDP 的产品对比

更新日期：2026-10-17。基线：当前仓库代码与查阅到的官方资料；未进行同环境三方性能实测。

## 1. 产品定位与结论

MiniStream 面向“把自己的 Windows 游戏主机画面和操作延伸到另一台 Windows 电脑”。RustDesk 面向跨平台远程控制与支持；Windows RDP 面向 Windows 远程桌面会话及相关管理场景。

**MiniStream 当前最可信的优势是用途集中、游戏参数可定制、围绕现有桌面工作，以及适配已有 IP/FRP 使用方式。低延迟和高帧率是它的优化目标，尚不是已经实测胜过其他产品的结论。**

对本项目最直接的游戏串流技术标杆其实是 Moonlight + Sunshine：它们同样围绕游戏画面与输入构建，并具备更完整的客户端和外设生态。[Moonlight 官网](https://moonlight-stream.org/)

## 2. 核心能力对照

| 维度 | MiniStream 当前状态 | RustDesk | Windows RDP | 对项目定位的意义 |
| --- | --- | --- | --- | --- |
| 主要任务 | 单用户 Windows 游戏串流 | 通用远控、协助与运维 | 远程桌面与应用会话 | 可优先投入游戏体验，减少通用功能负担 |
| 会话方式 | 捕获所选本地显示器，将输入注入当前交互桌面 | 常规远控工作方式是控制现有桌面 | 常规连接使用远程会话语义；具体取决于系统和部署方式 | 相对常规 RDP，更贴近继续操作已在物理桌面运行的游戏；此点不是对 RustDesk 的独有优势 |
| 接入方式 | IP/域名与口令；公网需自行配置可达路径 | 支持自托管、P2P 与中继，也有直接 IP 设置 | 基于主机地址及 Windows 身份；公网通常结合 VPN/网关等部署 | 已有 FRP 时与现有习惯一致；对普通用户未必更省事 |
| 平台 | 当前仅 Windows | 官方列出多个桌面、移动及 Web 平台 | 被控端版本与客户端能力存在限制 | Windows 专注可减少开发分支，但平台覆盖是短板 |
| 图形链路 | DXGI 采集、GPU 色彩转换、硬编候选、D3D11VA 解码与 D3D11 呈现 | 支持多种软件编解码及 H.264/H.265 硬件编解码 | 支持 GPU 及 H.264/AVC 等图形能力，取决于系统和配置 | 不能把“对手没有硬编/只能软件渲染”当卖点 |
| 游戏调整 | 分辨率、帧率、码率、锐化等直接面向串流；键鼠相对/绝对模式 | 以远控设置为主，具体游戏手感需测试 | 以远程会话配置为主，游戏和外设兼容需逐项测试 | 更容易围绕具体游戏建立参数和交互习惯 |
| 高帧率 | UI 提供 120/144/240 等选项，实际受采集、硬件和显示器约束 | 不在本文给出未经核验的统一上限 | 不在本文给出跨版本统一上限 | 选项值不能直接作为实测帧率优势 |
| 音频 | 系统声音下行，尚无完整麦克风回传 | 有音频等远控功能，随平台与配置而异 | 有音频、麦克风等重定向能力，受客户端和策略影响 | 语音游戏仍有功能缺口 |
| 办公辅助 | 未实现完整剪贴板、文件传输和多屏并行体验 | 提供通用远控相关能力 | 有丰富的资源及外设重定向机制 | 无需宣称全面替代通用远控和办公工具 |
| 安全 | 目前 HMAC 口令认证；未见媒体载荷认证加密实现 | 官方说明 P2P 端到端加密，并提供自托管选项 | 有 Windows 身份认证、NLA 等机制 | 本项目尚不能以“更安全”作优势 |
| 维护与扩展 | 源码可由项目所有者围绕自身设备修改 | 成熟开源项目，具备更广平台和部署能力 | 操作系统与企业生态集成较强 | 定制自由是优势，维护成本也由自己承担 |

外部事实依据：[RustDesk 功能文档](https://rustdesk.com/docs/en/)、[RustDesk 自托管说明](https://rustdesk.com/docs/en/self-host/)、[RustDesk 直接 IP 设置](https://rustdesk.com/docs/en/self-host/client-configuration/advanced-settings/)、[Microsoft RDS 支持配置](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/rds-supported-config)、[Microsoft 资源重定向](https://learn.microsoft.com/en-us/azure/virtual-desktop/redirection-remote-desktop-protocol)。不同客户端、平台、版本和策略的实际支持需另行核验。

## 3. 相对 RustDesk，可以成立的优势

### 3.1 游戏需求能直接决定产品设计

MiniStream 已经把串流帧率、码率、锐化、键鼠模式和悬浮状态集中在同一条使用路径中。后续可以按 FPS、赛车或手柄游戏分别调优，而无需承担完整通用远控平台的功能范围。

这属于产品聚焦和定制便利。它并不证明当前点击更可靠，也不证明相同网络下的延迟更低；现有输入与断流问题仍需完成此前方案。

### 3.2 对已有固定网络的用户，连接模型直接

对于已经维护好 FRP、知道主机地址的使用者，直接填写地址即可匹配当前习惯，不必额外搭建 MiniStream 专用设备发现和账户服务。

RustDesk 同样有自托管和直接 IP 能力，因此这里的优势是“本项目默认围绕这种固定场景组织”，不是“只有本项目支持私有部署”。没有 FRP 经验的用户反而可能更适合成熟产品的发现与中继流程。

### 3.3 可以为自己的设备组合做针对性修改

项目规模和目标较集中，适合针对固定显卡、显示器与游戏修改采集、编码、工具栏或快捷键。维护者可以直接决定实验和发布节奏。

这不是源码开放性的独占优势：RustDesk 也有公开源码。本项目当前未附开源许可证，不能把“可自由二次分发”列为优势。

## 4. 相对 Windows RDP，可以成立的优势

### 4.1 继续控制主机当前的游戏画面

MiniStream 从本地显示器采集画面并向当前桌面注入输入，目标是“接着玩这台机器已经在运行的游戏”。相对常规 RDP 远程会话，这种工作方式更贴合物理显示输出和既有游戏进程。

这是根据本项目实现与 RDP 常规使用方式作出的架构判断。RDP 包含会话重连、服务器及其他部署情形，不能笼统写成“RDP 永远新建独立桌面”“RDP 一定无法接管已有会话”或“RDP 一定不能玩游戏”。个别游戏对会话、显卡和反作弊的限制须实际测试。

### 4.2 不依赖开启 Windows 内置 RDP 主机功能

MiniStream 作为独立 Windows 应用运行，其连接机制不依赖系统启用 RDP 主机。Microsoft 官方说明 Windows Home 不能作为内置远程桌面主机，而 Professional、Enterprise、Education 和 Windows Server 等版本可以。[Microsoft 远程桌面启用说明](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/remotepc/remote-desktop-allow-access)

因此对 Home 用户存在覆盖机会，但本项目仍需验证具体 Home 版本、图形驱动及权限，不能据此声称已经完成 Home 全版本兼容。

### 4.3 游戏画面的取舍可直接调整

编码参数、锐化和呈现方式由应用掌控，维护者可围绕游戏画面持续调整，也可在会话中直接展示相关控制项。对需要频繁切换串流参数的个人玩家，这种界面更贴近需求。

RDP 同样有硬件加速、编解码和体验策略。不能用“RDP 没有 GPU 加速”“RDP 永远只有低帧率”解释本项目优势。[Microsoft RDS GPU 加速说明](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/rds-graphics-virtualization)

## 5. 当前不宜宣传的说法

| 不宜使用的说法 | 更准确的表述 |
| --- | --- |
| 比 RustDesk、RDP 更快、更稳定 | 面向游戏低延迟调优，三方同环境结果待测 |
| 全程 GPU 零拷贝 | 部分处理在 GPU 完成；当前采集到编码仍有 staging 回读和系统内存输入 |
| 已支持 HEVC/AV1/HDR | 编码模块有 HEVC 基础，但当前会话固定 H.264；AV1/HDR 尚不能列为完成能力 |
| 支持 240fps，所以一定比其他产品流畅 | 提供目标帧率配置，实际呈现帧率与帧间隔需要验证 |
| 没有云，所以比其他产品安全 | 不依赖项目自建云账户；媒体保护、凭据存储和设备身份仍待完善 |
| 两个 EXE，无依赖，开箱即用 | 包含 FFmpeg 等运行依赖；公网可达性和可选驱动需要配置 |
| 游戏完全兼容、不会被反作弊限制 | 常规 Windows 游戏兼容性需要逐项验证，不能承诺所有游戏接受注入输入 |

本项目当前基础依据：`src/host/host_service.cpp` 固定 H.264；`src/host/capture.cpp` 与 `src/host/encoder.cpp` 存在 NV12 系统内存路径；`src/common/crypt.*` 提供 HMAC 认证，媒体发送路径未调用载荷加密。README 中部分较强宣传描述应以代码和实测为准。

## 6. 如何把“潜力”转化成“实测优势”

选择同一主机、客户端、显示器与网络，分别运行 MiniStream、RustDesk 和 Windows RDP；游戏标杆追加 Moonlight/Sunshine。每项保存版本、设置和实际协商参数；RDP 若导致会话或游戏运行条件不同，必须明确记录，不能当作完全相同条件下的延迟对照。

| 比较项 | 测量方式 | 何时能用于优势表述 |
| --- | --- | --- |
| 实际操作延迟 | 同一动作和场景，高速摄影测操作到可见反馈，给出分位数 | 多次测量有一致差异且条件披露完整 |
| 游戏流畅性 | 实际呈现帧率、帧间隔 P95/P99、冻结时间 | 连续动态场景稳定，而非只看 UI 目标帧率 |
| 清晰度与带宽 | 同码率对比及相似画质对比两套结果 | 不能通过明显降低画质换延迟后宣称全面领先 |
| 游戏兼容性 | 记录启动、窗口/全屏、键鼠和声音是否正常 | 只对实际测过的游戏与版本作结论 |
| 主机额外开销 | CPU、GPU、内存、编码占用和本机游戏帧率损失 | 用实测说明“更轻”，不只比较 EXE 个数 |
| 日常便利性 | 从启动客户端到可操作游戏的步骤和耗时 | 面向明确用户群，区分首次配置与再次连接 |

暂不填写猜测的排名和数字。已有回环日志、单一产品的性能数据和主观手感，均不能直接证明相对竞品领先。

## 7. 适用场景与推荐介绍语

| 用户需求 | 当前更合适的选择方向 |
| --- | --- |
| 自己维护 Windows 主机与 FRP，希望围绕游戏深度定制 | MiniStream 是可持续改造的专用工具；先完成稳定性修复 |
| 给他人远程协助、跨平台连接、需要较完整的通用远控能力 | 优先评估 RustDesk |
| Windows 办公、管理、需要身份与资源重定向集成 | 优先评估 Windows RDP，并核实版本及部署条件 |
| 希望尽快获得成熟游戏串流体验 | 优先对照 Moonlight + Sunshine，再判断自研的额外价值 |

建议对外介绍：

> MiniStream 是面向个人 Windows 游戏主机的轻量串流项目，支持 IP/域名连接及已有 FRP 部署，围绕游戏画面、键鼠和系统声音提供可定制的串流体验。它的价值是用途集中与便于定制；跨平台、通用远控、安全及外设能力仍在完善，性能优势以同环境测试为准。

本文只增加产品分析文档，不代表此前诊断方案或后续功能已经落地。在线资料查阅于 2026-10-17，涉及竞品的具体能力应在实际选型时按版本、平台和部署方式重新核验。
