# UDP 与连接质量排查（2.1.1 Preview）

## 本机实际发现

本机现有被控端安装目录是 `C:\Program Files (x86)\MiniStream-Host`。排查时后台 mslink 仍是旧文件（106496 字节，2026-10-23 00:13 构建），运行实例从 20:30 持续存在；目录内没有 `mslink-status.json`。单独打开新版控制台不会更新后台程序，也不会自动生成遥测。因此不能把面板缺数据直接归因于隧道未连接。

本机 UDP 14739 确实由 mslink 监听。该结果不证明公网 UDP 映射、服务商底层传输及回程都正常。仅知道公网服务器地址和两个端口，还不能确定故障在哪一跳；本轮未中断既有会话做公网认证探测，不宣称公网 UDP 已修好。

## 先让面板具备数据源

1. 结束当前远程会话后，安装新版完整被控端；注意沿用旧目录，避免同机留下 x86 / x64 两套安装和多个启动任务。不要仅替换 GUI。
2. 确认计划任务指向所升级目录，新 mslink 实例启动时间已改变。控制台应使用 `--root "实际被控端目录"`。
3. 检查该目录是否出现持续更新的 `mslink-status.json`。JSON 的 `pid` 应是新进程，`updated_unix_ms` 应持续改变。控制台要求 schema=1、role=host、采样在 5 秒内，并检查进程身份。
4. 新版控制台在读管理员进程路径被拒绝时，会退回核对 PID / 进程名并明确标注权限限制，不会把该情况直接当成离线。窗口打开错误目录、旧版后台、过期采样仍然不能显示新鲜质量数据。
5. 主控端也需升级。认证隧道连接后才有设备名与 RTT；真正开始串流后才有渲染帧率、丢帧和解码耗时。网络丢帧不是 IP 丢包率，隧道 RTT 不是完整输入到画面的延迟。

## 区分 UDP 故障阶段

打开主控端「性能与诊断」，持续观察约 15 秒并导出诊断。

| 指标表现 | 下一步 |
|---|---|
| `udp_probe_sent` 不增长 | 先检查隧道是否已经认证、程序版本与本地探测循环；不要先修改公网防火墙 |
| `udp_last_send_error` 非 0 | 按 Winsock 错误码检查本地 socket、路由或发送失败 |
| 已发送、有效 ACK 为 0，认证拒绝为 0 | 核对独立 UDP 映射和服务端收发抓包；无返回也可能是端口或过滤，不代表已确定回程单向丢包 |
| `udp_auth_rejected` 增长 | 优先核对两端版本、会话重连及 UDP 是否被转发到另一台主机/旧实例 |
| `udp_data_received` 增长但 ACK 计数为 0 | 已有认证数据证明存在 UDP 返回路径，应继续查 ACK 与版本兼容，不能称为整个回程不通 |
| ACK 曾增长、`udp_last_success_age_ms` 持续增大 | 排查 UDP 映射过期、链路抖动和服务端会话；检查是否频繁切换兼容通道 |

新版本提示为“未收到有效 UDP 探测应答，暂用 TCP”，不会仅凭探测超时就断言服务器回程不通。诊断计数按客户端连接尝试重置。

## 服务端与主机交叉确认

必须有两条独立的代理关系：公网 **TCP 14738 → 被控端 TCP 14738**，公网 **UDP 14739 → 被控端 UDP 14739**。TCP 可用不能证明 UDP 已配置。核对服务商控制台中 UDP 的实际协议类型、后端主机及本地端口，不要只看代理名称。

有服务器管理权限时，在连接尝试期间运行：

```sh
ss -lunp 'sport = :14739'
sudo tcpdump -nn -i any 'udp port 14739'
```

同时核对云安全组与主机防火墙的 UDP 规则。不要直接关闭整个防火墙。抓包若包含凭据/设备信息，不要原样公开。

Windows 被控端检查：

```powershell
Get-NetUDPEndpoint -LocalPort 14739
Get-NetTCPConnection -LocalPort 14738 -State Listen
```

如果服务端没有任何 UDP 入包，查客户端发送、外部端口与上游过滤；服务端有入包而主机没有，查代理转发；主机有入包和回包而客户端无有效应答，再查返回路径、会话与认证计数。应通过这些证据定位，而不是仅凭警告文字更换传输协议。
