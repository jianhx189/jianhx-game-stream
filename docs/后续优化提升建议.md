# MiniStream 后续优化提升建议

更新日期：2026-10-17。适用方向：Windows 游戏串流，主要通过已有 FRP 基础设施连接。

本文讨论完成当前稳定性改造后的增量方向，不重复此前提出的 TCP 可靠输入、点击与松键修复、坐标与工具栏事件归属、媒体连接隔离、弱网码率控制、UDP 探测切换及 FEC 路线。以下功能均为建议，不能作为已经实现的产品能力宣传。

## 1. 优先把“连接电脑”做成“进入游戏”

### 1.1 游戏库、应用启动与会话收尾（优先级 A）

参考 Sunshine 的应用配置思路，将“桌面”和用户自行添加的游戏作为连接入口。连接前选择游戏、显示器和专属配置，连接后直接进入对应场景，减少每次寻找窗口和修改参数的操作。

首版建议：

- 应用条目保存名称、可执行文件、参数、工作目录和图标；支持 Steam 协议链接，但只允许启动用户在被控端预先授权的条目。
- 每个应用保存分辨率、帧率、音频设备和画质偏好，桌面设置不覆盖游戏设置。
- 区分“断开串流”“退出游戏”“关闭客户端”；默认断开仅停止串流，不结束游戏。
- 启动失败显示具体原因；清理只针对本次启动且明确归属的进程，不能按进程名批量结束程序。
- 显示设置等临时变更先保存再执行，正常退出和异常重启后都能恢复。

验收：不借助远端桌面即可启动一个预设游戏；启动失败不遗留显示设置变更；断开不会误杀已有游戏。

参考：[Sunshine 配置文档](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2configuration.html)。应用入口是借鉴方向，以上授权及进程归属规则是本项目建议。

### 1.2 常用设备与首次连接向导（优先级 A）

参考 RustDesk 的设备入口和 Moonlight 的主机选择体验，增加设备卡片、最近连接、别名、收藏和每台主机独立设置。保持 IP/域名直连入口，不强制引入账户服务器。

连接前完成显卡、编码器、解码器、显示器和音频设备检查，展示“请求值”和“实际生效值”。没有硬解时明确说明并推荐较低档位，不能只因 FFmpeg 中存在编码器名称就判定硬编可用。设备在线检测不得触发正式会话或中断正在进行的游戏。

验收：用户第二次连接无需重填参数；能力不足时得到可操作的说明；设备卡片不把暂时不可达误报为密码错误。

参考：[Moonlight PC 客户端](https://github.com/moonlight-stream/moonlight-qt)、[RustDesk 客户端文档](https://rustdesk.com/docs/en/client/)。

## 2. 增加游戏所需的外设与声音能力

### 2.1 手柄透传与震动回传（优先级 A）

当前代码以键鼠输入为主。对客厅、笔记本和非 FPS 游戏，手柄是比通用文件传输更符合产品定位的增量。

先支持单个 XInput 手柄、摇杆/扳机、热插拔和震动回传，再扩展多手柄。客户端做校准、死区和设备选择；被控端明确展示虚拟手柄驱动是否可用。连接断开后恢复中立状态并移除本会话设备，避免产生“幽灵手柄”。

虚拟输入驱动属于额外安装组件，需评估维护状态、签名、授权和系统兼容性，不能把某个旧驱动存在当作长期可用保证。暂不承诺反作弊游戏兼容，也不通过内核注入绕过游戏限制。

验收：标准手柄测试程序与至少两款游戏通过按键、轴、震动和热插拔测试；无驱动时键鼠串流仍可使用。

参考：[Sunshine 入门与游戏手柄说明](https://github.com/LizardByte/Sunshine/blob/master/docs/getting_started.md)。

### 2.2 麦克风回传与音频设备选择（优先级 A）

系统声音下行已经存在，新增能力应聚焦客户端麦克风上行，以及指定游戏声音输出设备。需要虚拟麦克风时，将驱动作为可选组件，而非让用户误以为选择本地麦克风就能自动出现在远端游戏中。

- 麦克风默认关闭，提供清晰的开启状态、静音键和按住说话；连接关闭后停止采集。
- 优先实现单声道语音；处理采样时钟漂移、设备切换、拔插和占用失败。
- 扬声器外放时评估回声消除，耳机模式避免不必要处理；降噪提供开关。
- 区分“本机播放静音”和“远端游戏声音静音”，避免现有静音语义混淆。

验收：远端录音程序能收到客户端语音；麦克风关闭后采集停止；设备拔插不需要重启整个应用。

参考：[Microsoft 音频与设备重定向说明](https://learn.microsoft.com/en-us/windows-app/device-audio-folder-redirection-teams)。这里借鉴的是用户能力与设备生命周期，并非复用 RDP 协议。

## 3. 深化画面链路，而不是只增加分辨率选项

### 3.1 消除采集到编码之间的 GPU 回读（优先级 A）

当前 `src/host/capture.cpp` 的 GPU 转换路径仍通过 staging 纹理 `CopyResource`、`Map` 回读到 `Nv12Frame`；`src/host/encoder.cpp` 接受系统内存 NV12。因此“GPU 色彩转换”“硬件编码”和“全程 GPU 零拷贝”必须分开描述。

建议先选一种已实际部署的硬编后端做纹理直送实验：将同一适配器上的 NV12 纹理交给硬编接口，明确纹理所有权、同步与释放时点。保留现有系统内存路径作为兼容回退，再逐步覆盖其他厂商及多显卡设备。

验收：在相同画质与负载下，对照 GPU→CPU 回读量、CPU 占用、提交编码耗时 P95/P99、显存占用和游戏自身帧率。只有确认具体路径消除了回读，才标注该路径为 GPU 直送；无需承诺所有后端“零拷贝”。

### 3.2 编解码能力协商：HEVC 优先于 AV1（优先级 B）

编码器模块已有 HEVC 候选，但当前 `src/host/host_service.cpp` 创建会话时仍固定 H.264。应先把已有代码接成真正可用的能力协商，而不是直接在 UI 增加一个未经验证的选项。

客户端上报实际可初始化的解码能力，被控端测试硬编能力，在共同支持的格式中选择；首版默认 H.264，允许用户启用 HEVC，协商或初始化失败回退 H.264并说明原因。稳定后再评估 AV1。

验收：至少覆盖一组 HEVC 硬编/硬解组合、一组不支持设备及一次初始化失败；比较同等码率的画质与同等画质的带宽，同时记录编解码延迟。

参考：[Moonlight 支持能力](https://moonlight-stream.org/)。编解码选择应根据本项目实测，而非仅看其他产品的格式列表。

### 3.3 HDR、色彩正确性与文字清晰度（优先级 B/C）

先校准 SDR：明确 BT.709、全/有限范围、缩放和显示输出的处理，建立灰阶、近黑、饱和色、细字测试图。将锐化作为可选后处理，不能拿锐化代替正确采样和编码。

HDR 作为完整链路单独开发：10-bit 采集/转换、编码、元数据、客户端解码与 HDR 输出必须同时成立；SDR 客户端需要明确的色调映射。当前 NV12 8-bit 路径不能通过一个 HDR 开关直接升级。

4:4:4 或桌面文字优先模式放到后期；先衡量其硬件覆盖率和带宽代价，避免影响游戏主路径。

验收：SDR 无明显黑位抬升或压黑；HDR/SDR 混合设备无过曝；测试图和真实游戏均有留档对照。

### 3.4 显示管理与帧呈现模式（优先级 B）

参考 Sunshine 的显示设备管理，按客户端需求临时调整被控端分辨率、刷新率和目标显示器，断开后恢复。用稳定设备标识代替易变化的显示器序号。无头运行先支持可选的外部虚拟显示器，暂不自行开发显示驱动。

客户端提供“最低延迟”和“平滑呈现”两档，分别控制撕裂许可、同步和呈现节奏；验证 59.94/60、120/144Hz 等组合。当前关闭垂直同步是一种取舍，不能代表所有用户的最佳体验。

验收：全屏切换不闪退；休眠、显示器拔插与异常退出后可恢复配置；平滑模式改善帧间隔波动，并明确报告额外延迟。

参考：[Sunshine 显示设置](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2configuration.html)、[Moonlight 功能说明](https://moonlight-stream.org/)。

## 4. 从自用程序走向可维护产品

### 4.1 可信设备配对与凭据管理（优先级 A）

这是新增产品能力，不是此前传输可靠性修复的重复。当前 HMAC 用于口令认证，不等于音视频加密；README.github.md 的“自定义加密”描述与实际媒体发送路径不一致，后续应统一表述。

增加一次性配对码、被控端确认、设备身份与撤销列表；记住凭据时使用 Windows Credential Manager/DPAPI。采用成熟的认证加密方案保护控制与媒体，并验证身份绑定、nonce 唯一性和重放防护，避免自行设计密码协议。FRP 隧道保护只覆盖其实际加密区段，不能直接代替应用端到端保护。

验收：撤销设备不能重连；复制配置文件不能直接获得可用明文凭据；无效或重放数据不能驱动输入。具体安全协议另立设计评审，不在功能列表中随意选算法拼接。

参考：[RustDesk 安全与自托管能力](https://rustdesk.com/docs/en/)。

### 4.2 安装、更新与兼容性维护（优先级 A）

- 分开提供便携客户端与可安装被控端；FFmpeg DLL、可选驱动和系统前置条件有明确清单。
- 发布包内显示程序版本、协议版本、构建标识和依赖版本；变更记录写清兼容范围。
- 首版使用用户主动检查更新与手动安装；后续自动更新必须校验签名，并支持失败回滚与配置迁移。
- 维护 Windows、显卡、驱动及硬编/硬解组合矩阵；代码签名、依赖来源和许可证材料在正式分发前准备齐全。

验收：干净机器无需开发环境即可运行；更新失败保留上一个可用版本；缺 DLL 或不支持硬件能得到明确说明。

### 4.3 建立可信的产品性能证据（优先级 B）

在既有网络回归之外，新增物理“操作到画面反馈”测量与画质对照。程序时间戳估计的采集→呈现，不包含完整外设、游戏处理及屏幕扫描过程，不能直接等同于实际操作延迟。

固定机器、显示刷新率、游戏场景和画质目标，用高速摄影等方法测按下→反馈，并分别记录本机基线、MiniStream、Moonlight/Sunshine、RustDesk 和 RDP。记录版本及协商参数，公布 P50/P95/P99、最长冻结、游戏帧率损失和资源占用，不只公布最好的一次平均值。

验收：测试可复现；标明未测项；不能用不同链路、不同码率的数据得出“本项目更快”的结论。

## 5. 推荐实施顺序

| 批次 | 内容 | 完成后带来的价值 |
| --- | --- | --- |
| A1 | 设备收藏、能力检查、应用库及会话收尾 | 从反复配置变成快速进入游戏 |
| A2 | 手柄、麦克风和音频设备选择 | 覆盖更多游戏与语音场景 |
| A3 | 单后端 GPU 直送、安装分发、可信设备配对 | 降低主机开销并提高长期使用可维护性 |
| B | HEVC、显示管理、呈现模式、对照评测 | 形成可量化的体验提升 |
| C | AV1、HDR、4:4:4、多手柄增强 | 在基础能力稳定后覆盖高端需求 |

批次不是工期承诺。先完成此前稳定性方案，再按实际游戏需求安排 A1/A2；安全能力在扩大使用范围前完成。暂不优先做云账户、公共中继、多租户后台、完整文件管理和全平台客户端，避免把个人游戏串流扩展成通用远控平台。
